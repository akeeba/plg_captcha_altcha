# Security audit triage — plg_captcha_altcha

This file is a durable, checked-in record of security-audit findings that were reviewed and explicitly
**ruled not to be issues** (or ruled out of scope for this repo), together with the reasoning. Its
purpose is to stop future security audits from re-surfacing the same non-issues as new findings.

Read this file before running any security audit skill (`audit-*`) against this repository, and before
writing up findings. If a candidate finding matches an entry below, do not report it as a new finding —
reference this file instead and move on.

This file is **not** a substitute for `security.md` (the per-audit findings report, which is
`.gitignore`d and local). This file is the opposite: the small, stable subset of prior audit conclusions
that are expected to remain true across future audits, so it is checked into the repo.

---

## Ruled not-issues

### 1. Backend-only inputs that reach front-end output are not, by themselves, a vulnerability

**Example encountered:** admin-configured custom CSS colour/dimension plugin parameters
(`border_width`, `color_base`, etc. in `altcha.xml`) were interpolated into an inline `<style>` block
with no format constraint. Setting these values requires plugin-configuration access in the Joomla
backend (by default Manager or above).

**Ruling:** this is **not** a security finding, because it requires an already-authenticated,
already-authorised backend user — anyone with that access is inherently trusted with the site. The same
is true of countless core Joomla plugin/module settings (custom HTML, template overrides, editor-inserted
markup, etc.). Treating "a trusted backend user can enter content that ends up in front-end output" as a
vulnerability would flag most of Joomla core as well. There is no privilege-escalation or
cross-trust-boundary path here.

**However:** unvalidated backend input that reaches output unsanitised is still worth fixing as a
**functional/robustness bug** — a typo or bad value can silently corrupt output for every site visitor,
with no validation to catch it at entry or at use. When you find this pattern, report it as a functional
finding (not a security one), and prefer fixing it with matching validation at both the form layer
(Joomla XML `validate="regex"`) and the output layer (sanitize again before use, defence-in-depth) rather
than dropping it.

**How to apply:** before flagging a "backend-input reaches output" finding as a security issue, check who
can set the input. If it requires an authenticated, authorised backend session (plugin/module/component
configuration, not a public-facing form), it is not a vulnerability. Consider a functional-bug report
instead if the output isn't already validated/escaped.

### 2. Findings inside `src/Dependency/` (Mozart-vendored third-party code) are not this project's findings

**Applies to:** anything under `plugins/captcha/altcha/src/Dependency/` — this is generated by Mozart,
which rewrites the `altcha-org/altcha` namespace into `Akeeba\Plugin\Captcha\Altcha\Dependency\...` so
multiple extensions bundling the same library don't collide in the Joomla autoloader (Joomla core itself
may also bundle a different version of the same library). Placement under our namespace/source tree does
not make this code ours to patch.

**Example encountered:** `verifySolution()`, `verifyFieldsHash()`, and `verifyServerSignature()` in the
vendored `Altcha.php` compare HMAC/hash values with `===` instead of `hash_equals()` — a non-constant-time
comparison / theoretical timing side-channel.

**Ruling:** valid as an observation, but **not a finding to fix locally**. Per `AGENTS.md`, files under
`src/Dependency/` must never be hand-edited — they're regenerated by `vendor/bin/mozart compose`. The
correct actions, in order of preference:
1. Check whether a newer release on the *same* major version line already fixes it (safe, low-risk —
   `composer.json`'s existing version constraint usually already permits it) and bump if so.
2. If not fixed upstream, report it to the upstream project's issue tracker.
3. Do not adopt a new *major* version as a side effect of a security fix without a separate, deliberate
   compatibility review (breaking API changes are out of scope for an audit-driven dependency bump).

**How to apply:** when an audit skill finds something inside `src/Dependency/`, don't report it as a
project security finding. Note it, check for an upstream fix on the same major version, bump if a fix
exists, and otherwise flag it for an upstream report — never patch the generated file directly.

### 3. Joomla's global `secret` used directly as an HMAC/derivation key is correct, not a weakness

**Example encountered:** the plugin passes `$app->get('secret')` (Joomla's site-wide secret from
`configuration.php`) directly as the ALTCHA HMAC key, with no per-plugin key derivation (e.g. no HKDF).

**Ruling: not an issue.** This is documented and intended Joomla behaviour — `$secret` is meant to be
used as-is for exactly this kind of purpose (MD5 salts, HMAC secrets, etc.) across Joomla core and
extensions, with no further derivation expected. There have been proposals since as early as 2019 for a
dedicated per-extension/per-use-case secret-derivation API in Joomla core, but none have shipped. Until
one does, this project follows the documented, standard Joomla pattern deliberately — deviating from it
tends to create exactly the kind of non-standard behaviour that gets blamed on the extension (not Joomla
core) when something changes around it in a future Joomla release.

**How to apply:** do not flag direct use of Joomla's global `secret` as a weak-key / missing-domain-
separation issue in this project. This is a deliberate, standing decision, not an oversight.

### 4. SHA-1 as a selectable (non-default) CAPTCHA hashing algorithm is an intentional, documented trade-off

**Example encountered:** the plugin's hashing-algorithm option list includes `SHA-1` alongside `SHA-256`
and `SHA-512` (the default).

**Ruling: not an issue.** SHA-1 here is used purely as a proof-of-work/HMAC primitive for CAPTCHA
difficulty tuning, not for anything requiring collision resistance. Offering a weaker/faster hash is a
legitimate, informed trade-off for site owners who need a lighter CAPTCHA (e.g. for low-powered client
devices) — this trade-off is already documented for end users at
https://github.com/akeeba/plg_captcha_altcha/wiki/Configuration.

**How to apply:** do not flag the presence of SHA-1 as a selectable algorithm option in this plugin as a
cryptographic weakness. It's an intentional, documented configuration choice, not an oversight.

## How to keep this file useful

- When a future audit surfaces a *new* pattern that gets the same "not an issue, here's why" ruling from
  the project owner, add it here with the same structure (example encountered / ruling / how to apply),
  rather than letting the reasoning live only in a chat transcript.
- If a ruling above ever needs to change (e.g. Joomla ships a real secret-derivation API and the project
  decides to adopt it), update the relevant entry rather than leaving stale guidance in place.
- This file intentionally does **not** track fixed issues, in-progress work, or per-audit findings — that
  belongs in the (gitignored, local) `security.md` written by each audit pass.
